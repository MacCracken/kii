# kii — 2026-08-25 P-1 sweep (audit / refactor / hardening / optimization / security)

> **Status**: v1.5.1 deliverable. Five audit lenses over the full surface,
> every material finding put through an adversarial refutation pass.
> **41 raised, 2 refuted, 39 folded into 16 work items.**
> Predecessor: [`2026-05-22-audit.md`](2026-05-22-audit.md) (the M7 CVE-corpus
> walk, whose hardening checklist this sweep re-verifies).

## 1. Why this audit, and what it assumed

v1.5.0 broadened kii from two input formats to four in a single release, and did
so by re-pinning a dependency rather than by writing code. That is the shape
[ADR 0006](../adr/0006-adopt-chitra-decoder.md) intended, but it means capability
arrived without anyone reading the code paths it arrived through. This sweep
exists to read them.

Five independent lenses ran over the whole surface — correctness, security,
refactor, optimization, and docs + deferred-items — each blind to the others.
Every `high` or `medium` finding was then handed to a separate agent whose only
instruction was to **refute** it against real source, defaulting to "refuted"
when it could not positively confirm the claim. Findings that survived that pass
are below. Two did not, and are recorded in § 4.

The sweep assumed three things, all of which it checked rather than trusted:
that the M7(c) input-side hardening survived the v1.2.0 decoder re-fold intact
(**it did** — the dimension caps, IDAT accumulator cap, ratio cap and palette
bounds are all present in chitra 1.0.0); that the benchmarks still reproduce
(**they do**); and that the fuzz harness was exercising what it claimed
(**it was not** — see A-3).

## 2. What the sweep did NOT find

Stated because a report of only positives is not a report.

- **No memory-safety defect reachable from image content.** Every crafted-input
  path — malformed PNG/JPEG/BMP/GIF signatures, truncated streams, dimension
  bombs, palette-OOB, corrupt LZW — was refused cleanly. 6,011,000 fuzz
  iterations across eight surfaces are clean. The one memory-safety defect found
  (A-1) is reachable only through a command-line flag, not through file bytes.
- **No overflow in the emit buffer sizing.** The v1.2.1 bug class (a fixed
  per-row buffer overrun past ~89 columns) is genuinely fixed in both lanes. The
  per-cell budgets were re-derived from first principles: half-block is
  `fg(≤11) + bg(≤11) + glyph(3) = 25` against a `sw*26+16` allocation; ascii is
  `fg(≤11) + glyph(1) = 12` against `cols*14+16`. Both hold with margin.
- **No module-scope array-width bug.** CLAUDE.md warns that module-scope
  `var buf[N]` is `N × u64`, not `N` bytes. Every module-scope array
  (`palette.cyr`'s table, `ascii.cyr`'s 27-glyph coverage table) indexes
  consistently with its actual element width.
- **No `pstruct` layout error.** The 20 `STRUCT_*_OFFSET` slots end at 152, and
  all 37 declarations across `src/` and `tests/` are `[160]` — exactly the
  required size, function-scope, in bytes.
- **The dependency surface is honest.** All nine chitra names, all three
  darshana names and all thirteen cmdit names kii calls are inside their
  projects' frozen blocks with unchanged arity and return contracts. No
  `CHITRA_ERR_*` value was renumbered between 0.3.0 and 1.0.0.
- **No write path.** CLAUDE.md's "kii never writes files" holds: `src/` contains
  no file-creating call. Only tests write, and only under `/tmp`.
- **`--width` in every plausible range is safe.** A 120-case randomized matrix
  plus singles up to 20,000 all produced either a correct frame or a clean
  error. The defect in A-1 needs a width above ~2.5 × 10⁹.

## 3. Confirmed findings and repairs

### A-1 · HIGH · Unbounded `--width` wraps an allocation and the resampler writes past it

`--width` was read with no upper bound and flowed into
`_kii_compute_target_geometry` → `downscale_to_rgb`, where the allocation size is
the unchecked 64-bit product `dst_w * dst_h * 3`. `alloc()` rejects only `size <= 0`
and `size > ALLOC_MAX`, so a product that **wraps to a small positive value** is
honoured — and the nested resample loop then writes `(dy * dst_w + dx) * 3` bytes
past it.

Reproduced against the shipped binary: with a 1×1 PNG,
`kii --width 4611686018427387902 one.png` wraps `3 × (2⁶² − 2)²` to exactly **12**,
`alloc(12)` succeeds, and the process dies with **SIGSEGV (exit 139)**. Identical
on `--mode ascii`. Because the bump heap is walked forward linearly, this
corrupts adjacent allocations before reaching unmapped memory — an out-of-bounds
heap **write**, not merely a crash.

CLAUDE.md names this case directly: *"Do not trust external data (image files,
args) without validation — every parser path must bound-check."*

**Repair** — belt and braces. `KII_MAX_COLS = 100000` is enforced in `main.cyr`
before the value reaches the geometry layer, giving a real usage diagnostic
instead of a crash; and `downscale_to_rgb` independently refuses any geometry
whose product would overflow, using division rather than multiplication so the
check cannot itself overflow. The resampler is now safe for **any** caller, not
just the one call site. Regression tests pin both.

### A-2 · HIGH · A truncated JPEG rendered silently, and the comment explaining why was false

The `seen_iend` gate carried a JPEG arm's worth of confidence and no JPEG arm.
Its comment asserted that chitra *"reports 1 unconditionally for JPEG and BMP
(neither carries a trailer it tracks), so those never reach the warning"*. That
is true for BMP and **false for JPEG**: chitra sets the flag from a real `closed`
decision made by the scan driver — 0 when a scan ran out of data, or when the
last scan did not end at a real EOI marker.

So a truncated or EOI-stripped JPEG decoded to a partial frame, and kii rendered
that partial frame with no warning and exit 0. Verified: a 95 %-truncated
`gradient.jpg` produced a frame and an empty stderr.

**Repair**: the gate now has a JPEG arm
(`warning: incomplete JPEG (truncated scan or no EOI marker)`) plus a defensive
fallback for any future format, and the comment states what the code does.

### A-3 · MEDIUM · The 1,000,000-iteration PNG fuzz surface was testing nothing

Each decode fuzz iteration calls `alloc_reset()` to rewind the never-free bump
allocator — without it the heap grows ~22 KB per iteration. But `sankoch` caches
its CRC-32 table as a **lazy-init singleton holding a heap pointer**
(`lib/sankoch.cyr:327` `var crc32_table = 0;` with `:334` allocating it once and
skipping re-init forever after). `alloc_reset()` rewinds the allocator out from
under that pointer, so from **iteration 2 onward** the cached table aliased live
decode memory.

Measured by instrumenting the harness to tally return codes: **2999 of 3000**
iterations returned `PNG_ERR_NOT_PNG` — dying at the signature check, never
reaching the chunk walker, inflate, unfilter or the PLTE bounds. With
`alloc_reset()` disabled the same seed produced 1387 `HEADER` / 97 `CHUNK` /
1 `NO_IDAT`, i.e. a decoder actually under test.

**Repair**: every `alloc_reset()` in the harness is paired with
`crc32_table = 0`, forcing a re-init into the fresh heap. The post-fix tally is
**identical to the no-reset run**, while the heap stays bounded. All four decode
surfaces got the pairing, and the requirement is documented in `CONTRIBUTING.md`
so the next surface does not repeat it.

### A-4 · MEDIUM · The ANSI-injection sanitizer covered C0 but not C1

`kii_path_has_control_bytes` rejected C0 (except allow-listed TAB/LF) and DEL —
and passed the entire **C1 range 0x80–0x9F**, where a terminal in 8-bit mode
reads `0x9B` as CSI, `0x9D` as OSC, `0x90` as DCS and `0x9C` as ST. The C0
spelling of an OSC injection was correctly suppressed while its exact 8-bit twin
went through untouched.

Verified with `od`: a filename of `9D 30 3B 50 57 4E 45 44 9C` — a complete
C0-free `OSC 0;PWNED ST` — reached stderr **byte-for-byte**, through the very
guard the M7(c) C1 hardening item exists to close. kii's stated target is
BBS/MUD-era terminal compatibility, which is exactly where 8-bit C1 handling
still lives.

**Repair, and a false premise corrected.** The obvious fix — reject `0x80–0x9F`
— is *wrong*, and the test suite had encoded that wrongness: an existing
assertion required `a\x80b` to be **safe**, justified in-comment as *"the audit
doc's initial recommendation to reject 0x80–0x9F was relaxed for UTF-8
ergonomics"*. A flat range test does break UTF-8 (`画` is `E7 94 BB`, `ч` is
`D1 87`), but the conclusion drawn from that was backwards: a **bare** `0x80` has
no lead byte, so it is not valid UTF-8 at all and no legitimate filename produces
it. The "ergonomic" relaxation *was* the hole.

The predicate now walks UTF-8 structure instead of testing a byte range, which
catches both real cases and neither legitimate one: a C1 byte standing where a
lead byte belongs (8-bit mode), and the two-byte spelling `C2 80`–`C2 9F` that a
UTF-8 terminal decodes back to C1. Malformed UTF-8 is refused on the principle
that if we cannot tell what the terminal will do with the bytes, we do not echo
them. `U+00A0` and the rest of Latin-1 Supplement still pass. The superseded
assertion now reads `unsafe`, with the reasoning recorded beside it.

### A-5 · MEDIUM · Every `write(2)` to stdout was unchecked

Both frame emitters called `syscall(1, 1, buf, n)` and discarded the result, then
returned 0. `kii img.png > out.ansi` on a full filesystem exited **0** having
written nothing, so a shell `kii … > out && use out` consumed the empty file
happily. `write(2)` is also permitted to return a **short** count, which would
have truncated the ANSI stream mid-row without a word.

**Repair**: `_kii_write_all` loops until the buffer drains, retries `EINTR`, and
reports real errors; both lanes propagate a distinct
`failed to write frame to stdout` diagnostic and exit 1. SIGPIPE keeps its
default disposition deliberately — `kii img.png | head` should die by signal like
any other Unix filter.

### A-6 · MEDIUM · `--color 8` was parsed, validated, and then ignored

`kii_validate_color` has range-checked `--color` since M1, and nothing ever
consumed the value: `kii --color 8` emitted output **byte-identical** to
`--color 16`, while the flag's own help text promised *"color tier: 8 or 16"*.

**Repair**: implemented rather than documented away — CLAUDE.md scopes tier-1 as
the *"8/16-color ANSI palette"*, so the flag describing a real tier is the
correct reading. `quant_set_tier` bounds the quantizer's search to the
normal-intensity half; the low 8 palette entries *are* the 8-colour tier, so no
second table exists. Verified: `--color 8` now emits indices 0–7 only, `--color 16`
is unchanged and every golden artifact is byte-identical.

### A-7 · MEDIUM · A JPEG could be told about the PNG § 11.2.2 bit-depth table

`_kii_map_chitra_err` routed `CHITRA_ERR_UNSUPPORTED` to `PNG_ERR_BITDEPTH`,
whose message cites the PNG bit-depth table. But that chitra code spans formats
by design (chitra ADR 0010 § 3): an unrecognised PNG critical chunk, a non-zero
compression or filter method, an unrecognised colour type, **or an Adobe APP14
colour transform chitra declines**. The last of those is a JPEG. This was the one
path that could produce exactly the outcome `PNG_ERR_UNSUPPORTED`'s own comment
says the two-code split exists to prevent.

**Repair**: mapped to `PNG_ERR_UNSUPPORTED`, whose meaning — *the file is valid;
chitra declines it* — is precisely this code's meaning. `CHITRA_ERR_BIT_DEPTH`
still maps to `PNG_ERR_BITDEPTH`; the split is the point, and a test now pins
both halves.

### A-8 · LOW · A 1-row terminal discarded its own valid column count

The winsize result was gated by one combined condition,
`detect_rc == 0 && term_cols > 0 && term_rows > 1`. The `term_rows > 1` clause
exists only so `term_rows - 1` stays ≥ 1, but it scoped over the whole
assignment — so on a genuine 1-row terminal (a status line, a CI pty, a tmux pane
dragged to one row) detection **succeeded**, reported a perfectly good column
count, and kii threw it away along with the rows, falling back to 80 columns and
emitting a frame wider than the terminal it had just measured.

**Repair**: columns and rows are decided separately; a 1-row terminal keeps its
single row.

### A-9 · LOW · `_emit_bg_256_buf` diverged from the darshana twin it mirrors

darshana 0.9.3 added a negative-`pos` guard to all seven of its `_buf` composers
after finding that a `-1` sentinel fed back in as a position wrote ESC at
`buf - 1` and returned a bogus positive length. kii's local BG-256 copy — which
sits in the *same per-cell chain*, taking the FG composer's return value as its
`pos` — never picked the guard up, so the two halves of one escape pair had
different contracts.

**Repair**: guard added, tests pin it. (The local copy itself stays: darshana
1.0.0 still does not ship `tty_bg_256_buf`, and its roadmap explicitly defers it.)

### A-10 · LOW · A benchmark vanished instead of failing

`tests/kii.bcyr` guards each system-fixture bench with
`if (kii_decode_png(path, &probe) == PNG_OK) { … }` and had no `else`. The
`1024²` fixture stopped shipping on this host, so that row silently disappeared
from the output while `docs/benchmarks.md` went on quoting `647 ms` for it — a
number nobody could reproduce and nothing flagged. All three guarded benches now
print an explicit `SKIPPED` line.

### A-11 · Documentation — nine files carrying claims the code had left behind

Corrected, each verified against the tree rather than read for plausibility:

- **`SECURITY.md`** claimed *"Adam7 interlacing + 1/2/4-bit depths both rejected
  with distinct errors"* — **false since v1.2.2**; `tests/decode.tcyr` asserts
  `PNG_OK` for exactly those inputs. Its fuzz, buffer-bounds and ANSI-filter
  bullets were also pre-re-fold. Rewritten.
- **`src/png.cyr`**'s `PNG_ERR_INTERLACE` comment said Adam7 was unsupported and
  **blamed the release that added it** (chitra 0.2.1). The code is an
  unrecognised-*method* check.
- **`docs/guides/getting-started.md`** quoted twelve error messages, **seven of
  which kii has not emitted since v1.2.0**, and listed interlace and sub-byte
  depths as rejections. Table rebuilt from `main.cyr`, including the three
  non-fatal warnings it never mentioned.
- **`docs/architecture/README.md` item 005** argued for keeping
  `quantize_nearest_image` — deleted at v1.2.0 — citing coverage in
  `tests/kii.tcyr`, retired in the same release. It was justifying the retention
  of code that did not exist on the strength of tests that did not exist.
- **`CLAUDE.md`** and **`README.md`** both still said BMP/GIF were *planned*,
  four months after they shipped; README's Status block read `v1.0.3`.
- **`CONTRIBUTING.md`** directed contributors to `tests/kii.tcyr` (retired) and
  published `287 assertions … as of v0.5.0`.
- **`docs/development/state.md`** listed the chafa visual review as deferred
  *"once chafa is installed"* — it **closed at v1.0.0**, chafa 1.18.2 is
  installed, and the link pointed at `chafa-comparison-deferred.md`, **a filename
  that has never existed**. Its binary-size figure was **4.6× low** (145 KB
  recorded, 668 KB actual).
- **`docs/benchmarks.md`** — see A-10 and the new v1.5.1 re-baseline.
- **`src/main.cyr`**'s file header described the M4 in-repo decoder pipeline
  five minor releases after the re-fold deleted it, and `--help` still advertised
  the ASCII lane as a *"luminance ramp"* four releases after shape-vector
  matching replaced it.

## 4. Refuted

Recorded because a refutation is a result.

- **"`PNG_ERR_CHUNK`'s inner `if/else` has two byte-identical arms"** — the code
  observation was correct and the arms *were* identical, but the finding was
  rated `medium` on a mechanism that does not exist: it is dead branching, not a
  wrong message. Downgraded to a cleanup and applied as one (the branch is
  collapsed), not carried as a defect.
- **"Three source comments describe `quantize_nearest_image` as still present"**
  — the staleness is real (and fixed under A-11), but the finding's load-bearing
  consequence and its count were both wrong.

## 5. Accepted risk

- **TAB and LF remain allow-listed in echoed paths.** This is a deliberate
  coreutils-`ls` convention, pinned by test. It does mean a filename containing
  a newline can split a kii diagnostic across two lines and forge what looks like
  a second message. Judged acceptable: the alternative refuses to name
  filesystem-legal files, and the forged text cannot contain control bytes.
- **PNGs above ~5.6 megapixels are refused with a misleading message.**
  `sankoch`'s `DECOMPRESS_MAX_OUTPUT` is 16 MiB, far below the 256 MB ceiling
  kii's own diagnostics advertise, so such a file reports
  `DEFLATE decompression failed (corrupt IDAT)` — wrong for a perfectly valid
  image. The cap is in vendored `lib/`, which kii must not edit; filed upstream
  and recorded in `state.md`.
- **~93 % of every render is `sankoch`'s Huffman decoder.** Also vendored, also
  filed upstream. There is no meaningful latency work available inside kii; see
  `docs/benchmarks.md` § v1.5.1.
- **The `png_*` / `PNG_ERR_*` / `png.cyr` names now cover four formats.** The
  rename to `image.*` / `IMG_ERR_*` stays deferred — it touches ~40 symbols
  across 8 source and 5 test files, which is a poor fit for a patch release — but
  the case for it is materially stronger than it was at v1.4.0 and it should be
  taken at the next minor.

## 6. Status after this audit

550 assertions green across five suites (was 511). 6,011,000 fuzz iterations
clean across eight surfaces, one of which was **measuring nothing** before this
cut. Linux, `--agnos` and `--aarch64` all build. Rendering is byte-identical at
the default colour tier — 22/22 golden artifacts across four formats, five
widths, both render lanes, `--verbose` stderr and `--help`.
