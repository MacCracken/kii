# kii — 2026-10-15 P(-1) sweep (audit / refactor / hardening / optimization / security)

> **Status**: v1.6.4 deliverable. Five audit lenses plus a dedicated
> verification of the three zlib CVE-class transfers, every material finding
> put through an adversarial refutation pass. **56 findings raised; 1
> MEDIUM, 9 LOW and 1 INFO repaired with regression tests (P-1 – P-11), 3
> byte-identical optimizations adopted, ~30 documentation corrections, 9 items
> deferred to a pinned version, 2 hypotheses refuted.** The three CVE classes
> **hold**.
> Predecessor: [`2026-08-25-audit.md`](2026-08-25-audit.md) (the v1.5.1 P-1
> sweep), whose method this repeats.

## 1. Why this audit, and what it assumed

Three releases in one day (1.6.1–1.6.3) moved every dependency kii links: cmdit
1.2.5 → 1.4.0, chitra 1.0.3 → 1.2.0, and cyrius 6.7.9 → 6.7.12, which brought
the stdlib's sankoch 2.8.3 → 2.8.7. Each was verified for byte-identical
output, but none read kii's own code again. The roadmap pinned this sweep to
1.6.4 so the 1.7 line opens on a re-read tree.

Six finders ran independently over the v1.6.3 tree (HEAD `63f98ec`):
correctness, security, refactor / code health, optimization, documentation
currency, and a CVE-class verification of the inflate kii links. Each MEDIUM,
each output-changing finding, and each claim with a number in it then went to
a separate refuter whose only instruction was to refute it against real source
and real runs, defaulting to "refuted" when it could not confirm. Every repair
below carries a test that fails against the pre-repair code (checked by
mutation where the test is new), and every change that alters output is
listed with the inputs it alters.

Assumptions checked rather than trusted:

- **The 6.7.10–6.7.12 language changes do not reach kii.** True: the 6.7.12
  compiler builds byte-identical binaries to 6.7.9 from the same sources
  (verified at 1.6.3, re-confirmed here).
- **sankoch is no longer kii's bottleneck.** True for large PNGs only: inflate
  is still 83 % of a RAMGON render, but on a 256² icon kii's own downscale,
  quantize and emit were 80–85 % of the run. § 3, P-12.
- **The fuzz harness tests what it says.** Mostly. The geometry surface could
  fail only by crashing (P-10).

## 2. What the sweep did NOT find

- **No memory-safety defect reachable from image content.** The security lens
  crafted inputs at chitra's caps (65535 per side, 16.7M px), special files,
  and every argv form; the CVE verification ran ~474,000 crafted DEFLATE
  streams under poison redzones. No crash, overrun or hang.
- **No escape injection through any output.** Palette indices are bounded
  below the tier before they reach darshana's SGR composers (which also reject
  anything outside 0–255); ASCII glyphs come from a fixed 27-entry printable
  table; `--verbose` prints only numbers and fixed colour-type names; and the
  1.6.2 `kii: --<flag> takes no value` line echoes only registration literals —
  `--verbose=ESC]0;…` and eight other hostile forms put zero ESC/CSI bytes on
  stderr.
- **No integer overflow at chitra's caps.** The largest product in kii's
  geometry is ~6.6e9; downscale's guard divides rather than multiplies.
- **No unchecked allocation.** Every `alloc` site in `src/` handles 0, and a
  0 cmdit handle reports NOMEM.
- **No regression of the v1.5.1 repairs** (A-1 width overflow, A-2 silent
  truncated JPEG, A-4 C1 sanitizer, A-6 `--color 8`, A-8 1-row terminal).
- **No process spawning** anywhere in `src/` or the three dependencies.
- **The dependency surface is honest**: all 11 chitra functions kii calls are
  frozen names in 1.2.0; `_kii_map_chitra_err` maps all 35 codes.

## 3. Confirmed findings and repairs

### P-1 · MEDIUM · An ordinary `--width` turned a 392-byte image into gigabytes of output

`--width N` derives the row count from the image's aspect with no limit
(`_kii_compute_target_geometry`). A 1×65535 GIF (392 bytes) or PNG (464
bytes), well inside chitra's caps, at `--width 80` asked for 2,621,400 rows: the
refuter measured 1.56 GB RSS at 130 s with nothing written yet, then a
predicted 4.42 GB of ANSI (output is exactly `⌊65535·w/2⌋ × (21·w + 5)` bytes).
Only `downscale_to_rgb`'s `ALLOC_MAX/3` guard bounded it, at `--width 104`
(~7.5 GB of output). The fit path (no `--width`) was always bounded by the
terminal. `KII_MAX_COLS` existed only to stop an integer wrap.

**Repair**: `KII_MAX_CELLS` = 1,048,576 character cells (`src/cli.cyr`), checked
by `kii_frame_cells_ok(cols, rows)` (division form, no overflow) after geometry
on both lanes and both paths: `<path>: frame too large (over 1048576 cells);
use a smaller --width`, exit 1. A 4M-cell cap was tried first and still let
the same GIF write 45 MB at `--width 8`; at 1M the worst case is ~26 MB of
output and ~19 MB of buffers, and `--width 1000` of a square image (500,000
cells) still renders. **Tests**: 11 boundary cases in `tests/cli.tcyr`, and the
geometry fuzz surface now checks the predicate against the plain product.

### P-2 · LOW · The file read misreported everything that is not a regular file

`kii_file_size` sized the file with `lseek(SEEK_END)`, then `file_read_all`
opened it a second time. So `cat x | kii /dev/stdin` and `kii <(…)` said
"cannot open file" (ESPIPE); an ext4 directory said "file exceeds size ceiling
(max 256 MB)" (its htree EOF is ~2^63; on tmpfs the same lseek gave EINVAL and
"cannot open file"); a FIFO with a writer said "cannot open file"; and the
path could change between the size check and the read. **Repair**: the
stdlib's `file_read_whole_max(path, KII_MAX_RAW_BYTES, &n)` — one open, read
to EOF, `-EFBIG` past the cap, `-EISDIR` for a directory. New
`PNG_ERR_IS_DIR` (18): `is a directory, not an image file`. Pipes, `/dev/stdin`,
process substitution and FIFOs now render. `KII_MAX_RAW_BYTES` is now defined
as chitra's `CHITRA_MAX_RAW_BYTES` (both 256 MB, pinned). **Tests**: a directory
→ IS_DIR; the cap pin. Pipes are verified end to end (an in-process test
cannot open a pipe as a path).

### P-3 · LOW · Transparent pixels rendered their hidden colour

kii dropped alpha. chitra keeps a GIF's transparent palette entry's RGB at
alpha 0, so a GIF whose transparent index is magenta drew magenta where the
image is empty; PNGs storing `rgba(255,255,255,0)` drew white. ADR 0006 had
recorded the drop as deliberate ("ready for any future alpha-compositing
tier"), so the refuter rated it LOW, not MEDIUM. **Repair**: composite over
black, `(c·a + 127) / 255` (`_over_black`, `src/downscale.cyr`), on both the
fast path and `_extract_rgb`. Exact at the ends: alpha 255 returns `c`, so
every opaque image is byte-identical. **Measured**: of 466 system images, all
325 whose output changed are non-opaque, and all 129 opaque ones are
byte-identical. Real transparency (the terminal's default background) is
pinned to 1.8.0. **Tests**: 3 rewritten and 10 new assertions (both paths,
alpha 0 / 128 / 200 / 255).

### P-4 · LOW · Decode diagnostics: format-blind for GIF, wrong for zero dimensions, untested

- A corrupt GIF LZW stream printed `DEFLATE decompression failed (corrupt
  IDAT)`, and an image-less GIF `no IDAT chunks` — against ADR 0009's rule
  that a format kii renders is a format it can name in an error. Now `corrupt
  GIF image data (bad LZW stream)` and `no image in GIF (no image descriptor)`.
- chitra raises DIMENSIONS for a 0 width or height in every format; the line
  said only "exceed policy ceiling". Now `image dimensions are zero or past
  the policy ceiling (…)`.
- OS/2 Huffman 1D and `BI_CMYK` BMPs got "(bit depth, BI_JPEG/BI_PNG
  compression, or channel mask)", naming neither. Now "(bit depth, compression
  method, or channel mask)".
- The GIF warning said "tail zero-filled"; chitra fills with palette entry 0 at
  full alpha, which rendered white in the finder's sample. Now "(image data
  ran out; the rest is drawn in palette colour 0)".
- All of it lived inline in `main`, where no test could reach it.

**Repair**: `kii_decode_error_text(rc, fmt)` and `kii_incomplete_warning_text(fmt)`
in `src/png.cyr`; `main` prints what they return. **Tests**: every line, per
format (29 assertions).

### P-5 · LOW · A negative `--width` silently meant "fit the terminal"

`--width -5`, `--width=-5`, `-w -5` and `--width -100000000000` all rendered the
auto-fit frame and exited 0. **Repair**: `kii_width_error_line` (`src/cli.cyr`)
refuses it: `kii: --width must not be negative (0 = fit the terminal)`, exit 2.

### P-6 · LOW · `--verbose` claimed a 16-colour render under `--color 8`

The summary ended in the literal `→ 16-color`. It now prints `quant_tier()`.

### P-7 · LOW · A TTY reporting 0 rows got no prompt row

A measured 24-row pty got 23 frame rows; a pty reporting 0×0 or 0×80 — how a
serial line or an un-negotiated telnet session looks — got 24, scrolling the
frame's top row off a real 24-row screen. **Repair**: `_kii_term_envelope`
gives a measured TTY with 0 rows `EMIT_DEFAULT_ROWS - 1`. Off a TTY the frame
is unchanged (80 × 24). **Tests**: the two envelope pins updated; the fuzz
envelope surface failed 83,256 of 1M iterations against the new rule until its
reference was updated — the surface working as intended.

### P-8 · INFO · The pstruct was never zeroed

`var pstruct[160]` is uninitialized stack (the refuter measured 160/160 bytes
nonzero after a prior call). The adapter wrote 11 of 20 slots on success and 1
on failure. In `main`'s fixed order every slot is written before it is read, so
nothing misbehaved — but the "has this stage run?" guards in quantize and emit
were dead. **Repair**: `kii_decode_png` zeroes all 20 slots first. **Tests**: a
garbage-filled struct is all zero after a failed decode, and the downscale /
quantize slots are 0 after a successful one.

### P-9 · LOW · Raw syscall numbers (carried in from the roadmap)

The test, fuzz and bench entry points exited with `syscall(60, …)` (x86_64's
`exit`; correct on aarch64 only because the backend renumbers it; `winsize` on
AGNOS), and five `src/` writes used `syscall(1, …)`. **Repair**: `SYS_EXIT` in
the seven entry points (matching `src/main.cyr` and `src/test.cyr`) and
`sys_write` in `src/`. A failing suite still exits 1 on x86_64 and aarch64.
The hypothesis that the raw 3-argument write could run non-blocking on AGNOS
(whose write takes a 4th "nb" argument) is **refuted** (§ 5).

### P-10 · LOW · Tests that checked less than they claimed

- `fuzz_geom_iter` checked only that each helper returned 0 or -1 — the only
  values either can return. It now checks the contract (success iff the source
  has both dimensions; exact `--width` geometry; fit inside the envelope; the
  frame-cell predicate). **Mutation-proven**: an off-by-one in the `--width`
  row count fails 999,970 of 1M iterations; a `>` → `>=` in the cell predicate
  fails 91.
- R-10: `_kii_map_chitra_err` falls back to HEADER for an unknown code — how
  INFLATE_LIMIT read as "malformed PNG" through v1.5.2. A test now pins chitra's
  code space (1–35 named, 36–98 not), so the next new code fails the suite.
- `-m` and the `--mode` default were never asserted; now they are.
- A false label ("JPEG seen_iend forced 1"), a stale comment
  ("UNSUPPORTED→BITDEPTH") and a duplicated assertion in `tests/decode.tcyr`.

### P-11 · LOW · Usage text that gave wrong advice

- The bundled-flag error told `-w5` and `-v=1` users to "use -x -y, not -xy".
  Now: `kii: short flags take no attached value and cannot be bundled (use -w
  40 -v, not -w40 or -wv)`.
- `--help`'s example said `render to terminal (80x24)` (the 80×24 is the
  non-TTY fallback), and `--mode`'s help printed "(default)" twice.

### P-12 · Optimization — three byte-identical speedups adopted

Measured by the optimization lens with a stage-timer harness and deterministic
instruction counts (the host's load average ran 7–25). RAMGON 80×24 is now
214.6 ms, of which inflate is ~178 ms (83 %), unfilter 9 %, chitra's RGBA pass
3 %, and **kii's own stages 0.6 %**. But a 256² icon decodes in 3.4 ms and
kii's stages were 80–85 % of the run — the v1.5.1 conclusion "no meaningful
latency work inside kii" holds only for large PNGs.

| | change | gain | identity check |
|---|---|---|---|
| **O-1** | `quantize_nearest_rgb` reads the packed palette inline (was 65 calls per pixel) | quantize ~4× | all 2²⁴ RGB values, both tiers; a 4,096-colour grid test against the old body in `tests/quant.tcyr` |
| **O-3** | `_ascii_match` loads the 6 regions once, walks the table by pointer, stops scoring a glyph once 3 terms reach the best (exact: the remaining terms are ≥ 0 and a win needs `<`) | ASCII emit ~2× | 20 M vectors against the old body |
| **O-4** | an RGBA fast path in `downscale_to_rgb` | downscale ~4× | the 476-run output matrix |

Measured end to end (`docs/benchmarks.md` § v1.6.4, whole process including
exec): a 256² icon at `--width 200` renders in 7.7 ms (was 16.7), in ASCII mode
11.5 ms (was 22.8), and at the default 80×24 3.7 ms (was 4.3); RAMGON is within
noise. The lens's own prototype reached ~3.6× on the icon by adding O-2's memo,
which was not taken (§ 6). `_color_dist2`, dead after O-1, is removed.

## 4. The zlib CVE-class transfers — verified, nothing to file

The 2026-05-22 audit recorded three zlib CVE classes as "spec-level
transfers" to file against sankoch; they were never filed. Verified here
against the sankoch kii links (2.8.7, byte-identical to cyrius 6.7.12's stdlib
and to sankoch's own `dist/`):

| class | verdict | the covering check |
|---|---|---|
| **CVE-2004-0797** (crash on malformed input) | **HOLDS** | Since 2.8.6 every caller checks `_huff_build`'s result, and a rejected set empties its tables; every malformed path (bit-reader EOF, stored LEN/NLEN, BTYPE 3, length 286/287, distance 30/31, zlib header, trailer, Adler-32) returns an error |
| **CVE-2005-1849** (oversized dynamic table) | **HOLDS by construction** | Fixed 512-entry 9-bit root tables with no variable sub-tables, so no ENOUGH/MAXD analogue exists; longer codes decode by count/offset capped at 15 bits; HLIT ≤ 286, HDIST ≤ 30, HCLEN 4–19 |
| **CVE-2005-2096** (incomplete code, length > 1) | **HOLDS** | Kraft incompleteness rejected before any table is built — zlib's `inflate_table` rule — and over-subscription likewise |

**Evidence**: a harness placing every stream in its own allocation with 4 KB
canary guards, built plain and under `CYRIUS_POISON` (redzones on every
`alloc`, including sankoch's tables), against Python zlib 1.3.2 as the
reference verdict: 95 hand-built targeted streams, 73,806 every-byte
truncations, 300,000 mutants (63,299 accepted by zlib, each byte-identical in
sankoch), and 100,000 random dynamic headers — **0 crashes, 0 guard or poison
violations, 0 verdict disagreements** (bar the deliberate 16 MiB ceiling). OOM
injection at each of sankoch's first 17 allocations returns cleanly. Through
kii end to end, seven malicious streams wrapped in valid PNGs each print
`DEFLATE decompression failed (corrupt IDAT)`, exit 1. **Not covered**: stack
buffers and source over-reads (poison guards heap writes only; both rest on
review of the index ranges), and the streaming decoder kii does not use.

## 5. Refuted

- **"A raw 3-argument `syscall(1, …)` write can run non-blocking on AGNOS."**
  AGNOS's write takes a 4th argument (`nb`; 0 blocks), and `_kii_write_all`
  treats a 0-byte write as fatal. The disassembly shows the compiler zeroes
  `r10` (`xor %r10d,%r10d`) before every syscall with fewer arguments, so the
  raw write already blocked. The writes moved to `sys_write` anyway (P-9).
- **"`tc & 2 != 0` in `tests/quant.tcyr` parses as `tc & (2 != 0)`."** Cyrius
  binds `&` tighter than `!=` (checked with a probe), so the cube-corner loop is
  right.

## 7. Accepted risk

- **Unicode bidi and format characters pass the path sanitizer** (U+202A–202E,
  U+2066–2069, U+200E/F, U+061C, U+2028, U+FEFF). They are valid UTF-8, not
  control bytes; on a bidi-rendering terminal an RLO in a filename reorders how
  the rest of the diagnostic line displays. Less than the accepted TAB/LF risk,
  which can forge a whole second line. The 2026-08-25 audit's "the forged text
  cannot contain control bytes" stands but is qualified here.
- **A FIFO with no writer blocks in `open()`**, as `cat` does. Ordinary Unix
  semantics; not a hang kii can cause on its own.
- **The slurp grows its buffer geometrically** on a never-free allocator, so a
  file near the 256 MB cap costs up to ~2× in transient memory (the old exact
  allocation cost 1×). Image-sized files cost a few MB.
- **PNG above ~5.6 MP of 8-bit RGB (≈4.2 MP of RGBA) is still refused** at
  sankoch's 16 MiB `DECOMPRESS_MAX_OUTPUT`; gated on chitra 1.3.0
  (`zlib_decompress_capped`).

## 8. Status after this audit

**709 assertions** across five suites (was 642): cli 141 → 163, quant 125 → 123
(the dead-helper group replaced by the reference-equivalence grid), render 188
→ 198, ascii 17, decode 171 → 208; passing on x86_64 and under
`cyrius test --aarch64`. **8,011,000 fuzz iterations** across ten surfaces,
clean. Host, `--agnos` and `--aarch64` build with zero warnings. Against v1.6.3:
every opaque image renders byte-identically (130 standard cases and 466 system
images compared); the output changes are exactly the transparent images (P-3),
the new and reworded diagnostics, and the two `--help` lines.
